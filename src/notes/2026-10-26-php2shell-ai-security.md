## PHP 高風險漏洞事件：AI 如何改變網路安全

### 一、事件背景

2026 年 10 月，PHP 被揭露存在兩個高風險漏洞，可能讓攻擊者在特定環境下，無須登入便從遠端攻擊網站。

這次事件引發多個組織採取緊急措施，包括網站進入維護模式、暫時下線，以及緊急準備安全更新。

#### 為什麼影響這麼大？

根據影片引用的 W3Techs 統計，截至 2026 年 10 月 22 日，在已知後端語言的網站中，有 **69.3% 使用 PHP**。

PHP 普及的原因：

- **容易學習**：能快速建立可運作的網站。
- **免費且開源**：任何人都可以使用。
- **生態系成熟**：大量網站及內容管理系統依賴 PHP。

例如 WordPress 使用 PHP 處理登入、商品資訊、訂單及資料庫操作。因此，PHP 核心出現漏洞時，影響可能遍及大量網站。

### 二、PHP 在網站中扮演什麼角色？

可以把網站想像成一家餐廳：

| 網站元件 | 餐廳比喻 | 作用 |
| --- | --- | --- |
| Frontend 前端 | 裝潢、菜單 | 顯示畫面及按鈕 |
| PHP 後端 | 廚師 | 處理請求與業務邏輯 |
| Database 資料庫 | 冰箱 | 儲存使用者、商品及訂單資料 |
| Browser 瀏覽器 | 顧客看到的畫面 | 顯示後端回傳的內容 |

當使用者按下登入或結帳時，PHP 會處理請求、存取資料庫、計算結果，再將內容回傳給瀏覽器。

**重點：後端不只是產生網頁畫面，也可能掌握使用者資料、身分驗證及交易流程。**

### 三、兩個漏洞如何運作？

影片以廚師、訂單、便條紙及抽屜的比喻，說明程式在處理記憶體時出現的問題。

#### 1. 漏洞一：CVE-2026-109618

**概念：記憶體溢位相關問題。**

影片描述的情境：

1. PHP 正在處理一個請求。
2. 請求超過記憶體限制，處理程序中止。
3. 某些尚未完成的中間狀態沒有被妥善清理。
4. 攻擊者可能利用這種異常狀態，影響後續程式執行。

影片指出，在 Apache 搭配 **mod_php** 等特定環境中，攻擊者可能在未登入的情況下觸發這個漏洞。

#### 2. 漏洞二：CVE-2026-109619

**概念：Use-After-Free（使用已釋放的記憶體）。**

意思是：程式已經釋放某段記憶體，後續卻仍然嘗試使用它。

可能的問題流程：

1. 程式釋放某段記憶體。
2. 舊的參照或指標仍然存在。
3. 後續請求使用了已失效的記憶體。
4. 程式可能讀取錯誤資料、崩潰，或在特定條件下遭到利用。

#### 3. 可能造成什麼後果？

影片描述的攻擊鏈可能包括：

- 洩漏部分伺服器記憶體資訊。
- 利用洩漏資訊推測記憶體配置。
- 嘗試控制伺服器的執行流程。
- 若成功取得 Shell，可能修改網站檔案、讀取資料庫密碼或留下後門。

Shell 在這裡指可以用來操作伺服器的命令介面。

需要注意：**能觸發漏洞，不代表一定能成功接管伺服器。** 影片指出，穩定完成攻擊仍有相當高的複雜度。

#### 4. 漏洞風險評分

影片引用的資料：

- 兩個漏洞的 CVSS 評分均為 9.2／10。
- CVSS 用來衡量漏洞風險，會考慮遠端攻擊條件、驗證需求及可能造成的影響。
- 影片提到的受影響系統數量估計差異很大，從數百萬到兩千多萬不等。

這些是影片引用的估計，並不代表所有相關系統都已經遭到入侵。

### 四、為什麼漏洞存在 14 年才被發現？

#### 1. PHP 的發展歷史

- **1995 年**：Rasmus Lerdorf 創造 PHP 的前身，最初用來管理個人網頁。
- **2012 年 3 月**：影片指出，相關問題可能從 PHP 5.4.0 開始存在。
- **2021 年**：PHP 社群更加重視核心維護人力不足的問題。

#### 2. Bus Factor：巴士因子

Bus factor 是軟體工程中的概念，指一個專案有多少關鍵成員離開後，專案就可能無法正常推進。

影片指出，PHP 核心維護工作曾高度依賴兩位主要工程師：

- Dmitry Stogov
- Nikita Popov

當 Nikita Popov 在 2021 年宣布將重心轉向其他專案後，社群開始更加關注 PHP 維護人力過度集中的問題。

**Bus factor 越低，代表專案越容易受到少數關鍵人員離開的影響。**

#### 3. PHP Foundation 的成立

2021 年 11 月，JetBrains 與 WordPress 背後的公司 Automattic 共同成立 PHP Foundation，為 PHP 核心維護工作提供資金支持。

這反映出開源軟體的現實：

- 任何人都能免費使用程式碼。
- 沒有單一公司負責所有維護工作。
- 專案能否持續發展，取決於社群與企業是否願意投入人力及資金。

**開源不等於不需要成本。** 程式碼可以免費取得，但安全審查、維護及漏洞修補都需要資源。

### 五、為什麼早期發現問題，卻沒有立即修好？

#### 1. 2024 年的安全稽核

根據影片，2024 年，德國政府相關的 Sovereign Tech Fund 支持外部安全稽核。

PHP 核心開發者在處理稽核報告中的問題時，發現這次漏洞的早期跡象。但當時還沒有找到具體的攻擊方法，因此問題沒有被列為最高優先級。

#### 2. 修補程式的困難

團隊提出過多種修補方案，但每種方案都有代價：

- 可能破壞舊有程式碼的相容性。
- 可能引入新的程式崩潰風險。
- 可能要求大量 PHP 擴充模組同步更新。

PHP 的擴充模組由全球不同開發者維護，修改核心設計，可能連帶影響整個生態系。

這就像改變整間廚房的插座規格，不只廚房本身要修改，所有設備製造商也可能必須配合。

#### 3. 結構性問題

當安全性、向下相容性、穩定性及生態系成本互相衝突時，團隊很難立即決定最佳方案。

影片指出，修補過程反覆推進又停下，持續數月。PHP Foundation 也承認，這反映出結構性的失敗。

### 六、AI 如何改變漏洞研究？

#### 1. AI 加速發現漏洞

影片提到，多個團隊在 2026 年使用不同 AI 模型及安全研究流程，幾乎在同一時期找到了這個存在多年的問題。

AI 的用途不只是掃描程式碼，還能協助研究人員：

- 找出可疑的程式碼路徑。
- 分析漏洞成因。
- 協助重現問題。
- 研究如何將漏洞轉化為可運作的攻擊方法。

#### 2. AI 的雙面性

AI 可以幫助防守方：

- 更快檢查大量程式碼。
- 找出人類可能忽略的漏洞。
- 加速分析、驗證及修補工作。

但攻擊者也可能利用同樣的能力：

- 更快定位漏洞。
- 自動化部分分析工作。
- 更容易研究攻擊方法。

**AI 不只降低防守方發現漏洞的成本，也可能降低攻擊者研究漏洞的成本。**

#### 3. 為什麼報告變多，不一定代表安全性變好？

影片指出，PHP 安全團隊自 2026 年 7 月 1 日起，發出了 15 個漏洞識別編號，但也處理了 106 份最終被判定為無效、重複或無法重現的報告。

這代表 AI 帶來的不只是效率提升，也可能增加安全團隊的審查負擔。因此，仍然需要人類判斷：

- 問題是否真的存在？
- 是否能夠重現？
- 嚴重程度如何？
- 修補方案是否安全？
- 是否會破壞既有系統？

### 七、漏洞為什麼會提前曝光？

#### 1. Coordinated Disclosure：協調式漏洞揭露

這是一種安全研究流程：

1. 研究人員私下通知軟體維護者。
2. 維護者分析問題並準備修補程式。
3. 相關組織協調公開時間。
4. 修補程式準備好後，再公開漏洞資訊。

目的在於避免攻擊者在修補程式推出前，就取得足以發動攻擊的資訊。

#### 2. 影片描述的事件時間線

| 時間 | 事件 |
| --- | --- |
| 2026/10/17 | Amazon 威脅情報團隊據稱觀察到相關攻擊嘗試 |
| 2026/10/20 | 漏洞識別編號提前在網路流傳 |
| 2026/10/21 凌晨 | 研究人員的漏洞利用示範影片短暫上傳，隨後被刪除，但副本已流傳 |
| 2026/10/21 | PHP 團隊提前公開漏洞資訊，修補程式也提前發布 |
| 原定 2026/10/22 | 原本預定的協調公開日期 |

影片也提到，修補程式在原定時間之前發布，讓原本依賴各方信任與時間協調的揭露流程受到衝擊。

#### 3. 這件事帶來什麼問題？

協調式揭露仰賴研究人員、維護者及雲端服務商共同合作。

但當漏洞資訊提前洩漏時，防守者可能還沒完成修補，攻擊者就已經開始行動。

這讓人重新思考：**當 AI 加快漏洞發現及攻擊研究的速度，傳統的漏洞揭露流程是否仍然足夠？**

### 八、開源軟體在 AI 時代面臨的挑戰

#### 1. 開源的優勢與風險

| 優勢 | 風險 |
| --- | --- |
| 全球開發者可以共同檢查程式碼 | 維護資源可能不足 |
| 任何人都能重複使用既有成果 | 安全責任可能分散 |
| 問題有機會被更多人發現 | 修補可能受到相容性限制 |
| 能快速共享改善成果 | 漏洞資訊也可能被攻擊者利用 |

#### 2. 防守者與攻擊者的不對稱

攻擊者只要找到一個可利用的弱點，就可能造成重大損害。

防守者則必須持續保護程式碼、伺服器、依賴套件及部署環境。當 AI 降低漏洞研究的成本，防守者就必須更重視：

- 更快發現問題。
- 更快驗證風險。
- 更快部署修補程式。
- 持續檢查是否已遭入侵。

### 九、網站管理者的五項防護措施

#### 1. 確認網站使用什麼技術

先確認網站使用的後端語言、框架及版本。可以詢問網站開發者、協助開發的 AI，或主機服務商。

#### 2. 檢查 PHP 版本並更新

影片列出的修補版本為：

- PHP 8.5.12
- PHP 8.4.27
- PHP 8.3.36
- PHP 8.2.35

實際更新時，應以 PHP 官方安全公告及所使用分支的支援狀態為準。

#### 3. 考慮使用代管主機

對沒有專職維運人員的網站，代管服務可能更容易維持安全更新。但仍應確認服務商是否負責 PHP 更新、安全修補、備份及異常監控。

#### 4. 分別更新 PHP 與 WordPress

**更新 WordPress 不等於更新 PHP。**

應分別處理：

- PHP 執行環境。
- WordPress 核心。
- 外掛。
- 佈景主題。

並移除不再使用的外掛，降低攻擊面。

#### 5. 清查所有網站，並檢查是否已遭入侵

除了主要網站，也要檢查：

- 多年前建立的活動頁面。
- 測試網站。
- 不再維護的舊專案。
- 忘記關閉的子網域或服務。

完成修補後，還應檢查更新前是否有可疑登入、異常檔案修改或其他入侵跡象。

**修補漏洞不代表過去沒有被入侵。**

### 十、一般使用者如何防範相關詐騙？

重大資安事件可能被詐騙者利用，常見手法包括冒充官方網站、寄送假連結，或利用緊急語氣要求使用者登入及下載檔案。

例如：

- 「發現重大漏洞，請在 24 小時內重新登入。」
- 「請立即重設密碼。」
- 「下載最新修補程式以保護裝置。」

防範方式：

1. 不直接點擊可疑訊息中的連結。
2. 自行搜尋官方網站並確認網址。
3. 必要時聯絡官方客服查證。
4. 在台灣可撥打 165 反詐騙專線諮詢。
5. 不因為訊息聲稱有重大漏洞，就隨意輸入帳密或下載檔案。

### 十一、總結：這起事件真正值得思考的事

#### 四個核心問題

1. **基礎設施依賴**：大量網站依賴少數開源專案，核心漏洞可能造成廣泛影響。
2. **維護資源不足**：軟體被大量使用，不代表維護人力與資金足夠。
3. **AI 的雙面性**：AI 同時提升漏洞發現及攻擊研究的效率。
4. **揭露流程的壓力**：漏洞資訊若提前曝光，防守者可能來不及完成修補。

#### 最重要的觀念

- 開源不代表有人會自動替你維護。
- 找到漏洞不等於已成功攻擊，但也不能忽略風險。
- AI 可以提高安全研究效率，也可能降低攻擊者的研究門檻。
- 更新只是安全管理的一部分，還需要監控、備份與入侵檢查。
- 網路安全不只依賴程式語言維護者，也需要企業、開發者、主機商及使用者共同承擔責任。

#### 延伸思考

1. 使用開源軟體的企業，是否應該負擔部分維護成本？
2. AI 發現漏洞後，應該如何決定公開資訊的時間？
3. 當漏洞修補速度追不上攻擊工具的發展，企業該如何調整安全策略？
4. 修補漏洞後，還需要哪些檢查才能確認系統沒有遭到先前的攻擊？
